# ADR 0001：两阶段生成 + 确定性版式引擎

- 状态：已采纳
- 日期：2026-10-30
- 决策者：项目作者

## 背景

让模型直接产出 PPTX 有三条常见路线：

1. **模型写 python-pptx 代码**：灵活，但坐标靠猜，十页里总有两三页溢出或错位；改一处版式要重写代码。
2. **HTML/CSS 模板 + 截图/转换**：视觉自由度高（Presenton、presentation_agent 的路线），但截图不可编辑，HTML→PPTX 转换会丢结构。
3. **结构化内容 + 固定版式**：模型只填字段，坐标由代码算（PPTAgent 的编辑式思路）。

## 决策

采用第 3 条，并把生成拆成两个阶段：

- `outline`：定版式、标题、要点，不写长文案。
- `compose`：按版式填字段，产出 `deck.json`。

版式实现为 9 个纯函数，输入 `slide` 与主题，输出 `Scene`。模型永远不接触坐标、字号、颜色。

## 后果

**好处**

- 版式稳定：溢出、越界、字号问题在写文件前就能算出来。
- 可评测：`deck.json` 是结构化的，断言可以精确到 `slides[0].layout`。
- 可回归：换模型不影响版式，换版式不影响提示词。
- 可预览：Scene 同时渲染 PPTX 与 HTML。

**代价**

- 设计自由度受限：新增视觉创意要写新的版式函数，不能靠模型即兴发挥。
- 不适合强品牌模板：本版不支持从用户 PPTX 继承母版；这是下一版（模板导入）的事。
- 长文案会被压缩或阻断：这是有意的——一页讲一件事。

## 备选方案为什么没选

- 模型写代码：失败模式不可控，评测只能靠肉眼；修复成本高。
- HTML 截图：交付物不可编辑，违背“可编辑 PPTX”的硬要求。
- 纯 Markdown（Marp/Slidev）：导出 PPTX 仍要转换层，且版式控制弱。
